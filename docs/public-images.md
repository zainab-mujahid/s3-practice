# Public restaurant images (Step 4)

The Owner manages the restaurant **logo** (one) and **dish images** (up to 50).
Everyone — Staff, Owner and anonymous visitors — can view published images.
Image bytes never pass through NestJS: the browser uploads them straight to S3
with a short-lived **presigned POST**.

```
React ──1 POST /api/admin/images/uploads──────────────► NestJS  session + CSRF + OWNER, validate, limits
      ◄──── uploadId + { url, fields } (presigned POST) ─        intent row (SQLite), key = staging/{uuid}
React ──2 multipart POST (fields…, file) ──────────────► S3      public bucket, staging/{uuid} (never public)
React ──3 POST /api/admin/images/uploads/:id/complete ─► NestJS  verify bytes → copy to logo|dishes/{uuid}.ext
      ◄──── { image: { assetId, url, … }, replaced } ───        → SQLite switch → delete staging + old image
Anyone ─ GET /api/public/images ──────────────────────► NestJS  SQLite only, returns public S3 URLs
Anyone ─ <img src="https://<public-bucket>.s3.<region>.amazonaws.com/dishes/{uuid}.png">  (bucket policy)
```

Code: `backend/src/images/` (API, limits, maintenance), `backend/src/storage/`
(Step 3 pipeline + `S3StorageService.createPresignedPost`), `frontend/src/api/images.ts`,
`frontend/src/components/OwnerImageManager.tsx`, `frontend/src/components/PublicGallery.tsx`.

## API

All paths are under `/api`. State-changing requests need the session cookie,
`Origin: http://localhost:5173` and `X-CSRF-Token` (existing global guards).
Guards run before body validation, so Staff/anonymous callers are refused before
any input is looked at.

| Method + path | Auth | OWNER | STAFF | Visitor |
|---|---|---|---|---|
| `GET /public/images` | none | ✓ | ✓ | ✓ |
| `GET /public/images/:assetId` | none | ✓ | ✓ | ✓ |
| `POST /admin/images/uploads` | session + CSRF | ✓ | 403 | 401 |
| `POST /admin/images/uploads/:uploadId/complete` | session + CSRF | ✓ | 403 | 401 |
| `DELETE /admin/images/:assetId` | session + CSRF | ✓ | 403 | 401 |

There is no separate "replace" endpoint: uploading a `LOGO` replaces the current
logo, and uploading a `DISH` with `targetAssetId` replaces that dish image (the
dish keeps its `assetId`).

### `GET /public/images` → 200

```json
{ "logo": Image | null, "dishes": [Image, …] }
```
`Image = { assetId, kind: "LOGO"|"DISH", url, contentType, sizeBytes, updatedAt }`.
No object keys, bucket aliases, staging keys or uploader IDs are returned.

### `GET /public/images/:assetId` → 200 `{ image }`
400 malformed id · 404 unknown id **or a private staff picture**.

### `POST /admin/images/uploads` → 201

Request (strict — any other field, e.g. `key` or `bucket`, is a 400):
```json
{ "kind": "LOGO" | "DISH", "targetAssetId": "<uuid, DISH only, optional>",
  "fileName": "pasta.jpg", "contentType": "image/jpeg", "size": 123456 }
```
Response:
```json
{ "uploadId": "<uuid>", "expiresAt": "<+300 s>", "completeBy": "<+10 min>",
  "upload": { "url": "https://<public-bucket>.s3.<region>.amazonaws.com/", "fields": { … } } }
```
| Status | When |
|---|---|
| 400 | Schema violation; size < 32 B or > 5 MiB; type not JPEG/PNG/WebP; extension ≠ type; `targetAssetId` on LOGO |
| 404 | `targetAssetId` is not an existing dish |
| 409 | 10 unfinished uploads already pending · 50 dishes already exist (new dish) |
| 429 | More than 20 requests/min from this client |
| 503 | Bucket names are still placeholders (no AWS call is made) · signing failed |

### `POST /admin/images/uploads/:uploadId/complete` → 200

```json
{ "image": Image, "replaced": true | false }
```
| Status | When |
|---|---|
| 400 | Malformed `uploadId` |
| 404 | Unknown upload, **another user's upload** (identical answer), not a public-image upload, or the dish to replace was deleted meanwhile |
| 409 | Already completed / rejected · being completed by a concurrent request · dish limit reached |
| 410 | The intent's 10-minute completion window has passed |
| 422 | Verification failed: `reason` ∈ `MISSING`, `EMPTY`, `TOO_LARGE`, `UNRECOGNISED_SIGNATURE`, `TRUNCATED_OR_CORRUPT`, `TYPE_MISMATCH`, `CHANGED_DURING_VERIFICATION`. The intent is rejected and its staging object deleted; start a new upload |
| 503 | S3 unavailable during verification/copy. The intent stays pending: retry `complete` |

### `DELETE /admin/images/:assetId` → 204
400 malformed id · 404 unknown id or a staff picture · 503 not configured.
If the S3 delete fails, the image is already unpublished (removed from SQLite)
and the object stays in the deletion queue for retry.

## Presigned POST controls

Generated by `S3StorageService.createPresignedPost` (AWS SDK v3
`@aws-sdk/s3-presigned-post`, signed locally — no AWS request). The signed policy contains:

| Condition | Effect |
|---|---|
| `{"bucket": <public bucket>}` | Only the public bucket |
| `{"key": "staging/<uuid>"}` (exact) | Server-generated key; no `starts-with`, no `${filename}`; the client file name is never used |
| `{"Content-Type": "image/png"}` (exact) | The type validated by the backend; verified again on the stored object |
| `["content-length-range", 32, 5242880]` | S3 refuses smaller/larger bodies |
| `expiration` ≤ 300 s | Enforced in code (`PRESIGNED_POST_TTL_SECONDS`); values above 300 s throw |
| `X-Amz-Algorithm/Credential/Date` | Standard SigV4 |

- S3 rejects form fields that the policy does not cover, so the browser can't add an ACL, metadata or a different key.
- `createPresignedPost` refuses final keys (`dishes/`, `logo/`, `staff/`) and any key outside the allow-list.
- **The 10-minute `s3:signatureAge` Deny is not relied on for the public bucket.** The sample public policy contains one, but your live public bucket may not. The 300 s expiration inside the signed policy is the control.
- **Size is enforced twice.** The backend rejects declared sizes outside 32 B…5 MiB (schema). After upload, the verifier checks the **stored** object size (HeadObject). S3's `content-length-range` is an extra layer; its exact boundary behaviour is part of the manual live checks below.
- The fields include `X-Amz-Credential`, which contains the IAM user's **access key ID** (not the secret). This is how every SigV4 presigned request works. The secret access key never leaves the backend.
- The upload URL and the published image URLs contain the **public** bucket name. That is unavoidable without a CDN (CloudFront would be a new AWS resource). The private bucket name is never sent to the browser.
- Presigned fields, URLs and signatures are never logged (the e2e tests assert this).

## Upload intents, concurrency and recovery

| Rule | Where it is enforced |
|---|---|
| Intent is bound to the user, the kind (`LOGO`/`DISH`) and the target dish | `upload_intents` row; `complete` checks the user and that the kind is public |
| ≤ 10 pending intents per user, ≤ 50 dishes | Checked and inserted in one `BEGIN IMMEDIATE` transaction (`createIntentWithinLimits`); the dish limit is re-checked inside activation |
| Completion only once, only while pending and unexpired | `activateUpload` re-checks inside `BEGIN IMMEDIATE`; `rejectIntent` is a conditional `UPDATE … WHERE status='PENDING'` |
| Only verified bytes are published | `CopyObject` with `CopySourceIfMatch` = verified ETag |
| The published image is never lost on a failed replacement | The asset row switches to the new key only in the activation transaction. Any earlier failure (verification, copy, SQLite) leaves the old image active, and an orphaned copy is deleted or queued |
| The old object is deleted only after the switch committed | It is queued in the same transaction; deletion happens after the commit, with retry on failure |

**Concurrency:**
- Two simultaneous `complete` calls for one upload: exactly one publishes. In one process the second gets 409 immediately. Across processes SQLite decides: the loser's activation fails and its copy is deleted. Both cases are tested; the second one bypasses the in-process check.
- Delete during a replacement: activation fails with "dish no longer exists" → 404, the copy and the staging object are removed, the intent is rejected.
- Two replacements of the same dish: last writer wins, and each replaced object is queued for deletion.

**SQLite cannot make S3 operations atomic.** Partial failures are handled by
ordering (copy → commit → delete), by compensating deletes, and by the
`pending_deletions` queue.

**`UploadMaintenance`** runs every 5 minutes (not in tests). It is idempotent and skipped while storage is not configured.
1. Pending intents past their deadline become `EXPIRED`, and their **staging** objects are queued for deletion. An expired intent can never be completed.
2. Queued deletions are retried with backoff. Right before each delete it re-checks that no active asset uses the key. Final keys are unique UUIDs that are never reused, so an active image is never deleted.
3. Finished intents older than 7 days are pruned.

The S3 lifecycle rule also expires everything under `staging/` after 1 day, as a backstop.

## Image verification limits

Verification checks the stored object's size, magic bytes, end-of-file/container
structure, and that detected type = declared type = stored Content-Type. **It
does not decode or re-encode the image and does not strip EXIF metadata**, so it
cannot prove an image is valid or harmless (see `backend/src/storage/magic-bytes.ts`).
Published images are only ever served as `image/*` with `Content-Disposition: inline`.

## Frontend behaviour

- The Owner dashboard's **Restaurant images** card shows:
  - the current logo and the dish images;
  - a file picker with a local preview;
  - staged status: requesting permission → uploading with a % bar → verifying and publishing;
  - Replace and Delete actions. Delete asks for a second, explicit confirmation.
- One operation at a time. Buttons are disabled while busy, so duplicate submissions aren't possible.
- Errors are mapped to plain messages: expired link, too large, S3 rejected, network/CORS, verification failure, permission, rate limit. Raw S3 XML (request IDs) is never shown.
- Only URLs returned by the backend after publication are rendered as images. Staging keys are never displayed.
- **Upload progress and CORS.** Listening to XHR upload progress makes the browser send a CORS preflight (`OPTIONS`).
  - The existing rule (origin `http://localhost:5173`, method `POST`, no extra headers) should allow it, but this is **not yet verified against real S3** (see the manual checks).
  - If it fails, the UI shows the network/CORS message. Review the rule before changing anything. Do not widen it.

## Tests

```bash
cd backend  && npm run lint && npm test && npm run test:e2e && npm run build
cd frontend && npm run lint && npm test && npm run build
```

All tests mock S3 (no AWS calls).
- `backend/src/storage/s3-storage.service.spec.ts`: decodes the signed policy and checks every condition, the expiry bound, and refusals.
- `backend/test/images.e2e-spec.ts`: the whole flow through the real app, including RBAC, CSRF, limits, throttling, verification failures, duplicates, concurrency, failed replacements, deletion failures and maintenance.
- `frontend/src/**/*.test.ts(x)`: API calls, FormData order, S3 error mapping, upload states, confirmation, role-based UI.

## Manual live checks (require separate approval — they write to real S3)

These are not run automatically.

**Cost:** a few PUT/COPY/GET/DELETE requests and a few KB of storage, which is far below one cent.

**Cleanup:** delete the images in the app. `staging/` also expires after 1 day.

|---|---|---|
| T01 | Upload a small dish image as Owner, then open its URL in a private window | 200 |
| T02 | Same for the logo | 200 |
| T22 | Anonymous GET of a `staging/…` object, using the key from the browser dev tools during an upload | 403 |
| T13 | Anonymous GET of any private-bucket URL | 403 |
| T23 | Replace the logo: the old logo URL returns 403/404 afterwards, the new one 200 | as stated |
| C1 | Network tab during an upload: the `OPTIONS` preflight to S3 returns 200 with `Access-Control-Allow-Origin: http://localhost:5173`, and the POST returns 204 | as stated |
